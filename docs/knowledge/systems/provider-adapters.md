## Summary

`gateway-providers` holds two adapters behind `ChatModelPort`, OpenAI (`.openai`) and Anthropic (`.anthropic`), over the provider-neutral `.upstream`. `POST /v1/chat/completions` reaches `ChatHandler`, `ChatCompletionService` resolves the deployment and calls the port, `RoutingChatModelPort` picks the adapter by the deployment's provider, and the adapter makes one upstream POST with the configured key. It hands status, headers and bytes to pure functions, which give a `ProviderResult`. OpenAI's wire is the gateway's shape, so its adapter forwards `extras`; Anthropic's is not, so its adapter holds a rule for every member and translates in both directions. Any upstream failure is a sealed `ProviderFailure`, which the mapper renders as one row of GW-01 section 4. A slow or absent provider costs at most `request-timeout`, and nothing is retried. With `stream: true` the same call is a cold flow of sealed events, translated chunk by chunk and written one flushed frame per event, committing the status at the first frame. Contract: [GW-01 spec](../../specs/GW-01-chat-completions.md), [GW-02 spec](../../specs/GW-02-sse-streaming.md) and [GW-03 spec](../../specs/GW-03-anthropic-adapter.md), section 4 of each.

## Contract (never break)

1. Provider types never cross the port. A stream is translated chunk by chunk, never buffered whole. Usage comes from the provider; an estimate is used only when the provider omits it, and is flagged `estimated`. ARCH-1, ARCH-12, ARCH-13, `internal` visibility, `ChatCompletionServiceTest`; for a stream `OpenAiChatStreamIntegrationTest`, `AnthropicChatStreamIntegrationTest`, `SlowClientStreamTest`, `StreamEndToEndTest` (timing).
2. Every outbound call has a connect timeout and a whole-call deadline; a stream has first-byte, idle and total deadlines. `OpenAiChatAdapterIntegrationTest` (`hang` with a 500 ms deadline), `OpenAiChatStreamIntegrationTest`.
3. An adapter never retries; retries and fallback are RTE-02's, before the first byte. `OpenAiChatAdapterIntegrationTest`: one failed call, one journal entry.
4. A provider's `message` is never relayed or logged; only `code` and `param` that pass the regex are. `OpenAiFailureClassifierTest`, `NoLeakIntegrationTest`.
5. The provider key is never logged or returned; the client's credential is never forwarded. `ApiKeyTest`, `StartupFailureTest`, `NoLeakIntegrationTest`, the journal fingerprint in `ChatCompletionsEndToEndTest`.
6. Provider response headers reach the client only through `retry-after` and `retry-after-ms`. `UpstreamErrorMappingTest`.
7. On the OpenAI path, members the gateway does not model pass through verbatim in both directions, `llmgw` excepted. `OpenAiShapeContractTest`, `ChatCompletionsEndToEndTest`, `OpenAiRequestWriterTest`.
8. A cancelled caller cancels the upstream call; `CancellationException` is never caught. `ClientDisconnectIntegrationTest`, `OpenAiChatAdapterIntegrationTest`.
9. A failure before the first frame is a status; after it, an SSE error frame with the same envelope, no `[DONE]`, and a clean end. `StreamUpstreamErrorMappingTest`, `StreamFailureIntegrationTest`.
10. The gateway always requests usage upstream; a client sees it only if it asked. `StreamShapeContractTest`.
11. No pooled buffer crosses into a `Flow`. `StreamBufferLeakIntegrationTest`.
12. A stream has exactly one end-of-stream report, whatever ended it. `StreamTallyTest`, `StreamDisconnectIntegrationTest`.
13. A foreign-shaped adapter has a rule for every member of the OpenAI request. What would change the output and cannot be honoured is a 400 `UnsupportedByProvider` with no upstream call, never a silent drop; a member set to `null` counts as absent. `AnthropicMemberPolicyTest`, `AnthropicRequestWriterTest`, `AnthropicChatEndToEndTest`.
14. A translated stream sends no chunk until it has output to show, so an error before that is a real status and fallback stays open. `AnthropicStreamDecoderTest`, `AnthropicStreamUpstreamErrorMappingTest`, `AnthropicThinkingRoundTripTest`.
15. `inputTokens` means every input token the provider processed, cached and cache-write included, on every adapter; `cachedInputTokens` is a subset. `AnthropicUsageReaderTest`, `AnthropicChatEndToEndTest`.
16. `llmgw` reaches no provider, except as a translation of what it holds for that provider, and an echoed thinking block keeps only its allow-listed members. `OpenAiRequestWriterTest`, `AnthropicRequestWriterTest`, `AnthropicThinkingRoundTripTest`.
17. A provider's `enabled` and its adapter's presence agree, or the start stops. `ProviderStartupTest`.
18. A vector is carried as its bytes and never parsed: a reply is byte-identical to the provider's, literals and whitespace included. `OpenAiEmbeddingReaderTest`, `EmbeddingsEndToEndTest`.
19. An embeddings call's reservations are released once on every path, and a full budget refuses before any upstream call. `EmbeddingBudgetTest`, `ReplyHoldTest`.
20. Work that grows with an embeddings body runs on the lane, never on `reactor-http-*` or `parallel-*`, and a full or closed lane is 503 `gateway_overloaded`, never 500. `EmbeddingThreadTest`, `OpenAiEmbeddingAdapterFailureTest`, `EmbeddingOverloadTest`.
21. A client that stops reading holds about one 1 MiB slice of a reply in the channel, not the reply. `EmbeddingSlicedWriteTest`.
22. A full lane refuses only a request's parse, never a stage after the upstream call, so a reply the provider sent is not dropped for load. `OpenAiEmbeddingAdapterFailureTest`, `CpuLaneTest`.

## How it works

- **Modules.** `gateway-core` holds the domain, port, service, estimator and reply table, and knows no JSON library or SDK. `gateway-providers` owns `spring-webflux` (WebClient only, with `spring-context` because its connector needs it), `reactor-netty-http` and Jackson's tree model. `gateway-app` holds the route, reader, writer, properties and wiring. Only `.gateway.app.config` names `.gateway.providers.openai` or `.anthropic` (ARCH-12); `.gateway.providers.json` is exempt. The two never name each other (ARCH-13): what they share is in `.upstream`.
- **`.upstream`** (ADR-GW-03-018). Everything neutral, composed rather than inherited: `UpstreamClient` (pool, `HttpClient`, `WebClient`, `exchange`, `warmUp`, `close`), `SseStreamCall` (the stream's POST, copy-and-release, the deadlines), `StreamLifecycle` over a provider's `StreamDecoder` (open, draining, ended, the terminal-event race), `TransportFailures`, `StreamDeadlines`, `RetryAfter`, `ProviderErrorFields`. A decoder is pure: an upstream event gives `Decoded.Open`, `Draining` or `Ended` with its events. `OpenAiStreamTranslator` is a `StreamLifecycle` over `OpenAiStreamDecoder`.
- **Selection** (ADR-GW-03-003, ADR-GW-03-020). `ProviderConfiguration` is the one place naming adapters. Each adapter is a `@Fallback` bean of its concrete type under `@ConditionalOnProperty`, so Spring's inferred `close()` runs, and `chatModelPort` builds a `RoutingChatModelPort` from those present, which is the one regular `ChatModelPort` candidate. `PrefixModelResolver` gives a model the first matching `model-prefixes` provider, else `default-provider`, and the deployment is named after its provider; prefixes load only for an enabled provider, so `claude-x` on an OpenAI-only start goes to OpenAI. A provider with no adapter is `ModelNotFound`. `x-gateway-deployment` tells the client which answered. RTE-01 replaces the resolver.
- **`enabled` flags** (ADR-GW-03-004). `llmgw.providers.<provider>.enabled` is explicit: OpenAI on, Anthropic off, Anthropic on in the `local` profile. Only an enabled provider's values are validated, and its `toAdapterConfig()` runs from the bean method. The start stops if no provider is enabled, if `default-provider` is not enabled, or if a flag and the adapter's presence disagree: the binder reads `1`, `yes` and `on` as true, the bean condition only `true` ([gotcha](../gotchas/conditional-on-property-and-the-binder-read-true-differently.md)). `client-write-timeout` stays below the lowest `idle-timeout` of the enabled providers (`ServerStreamConfiguration`).
- **Domain** ([patterns/typed-core-with-json-extras](../patterns/typed-core-with-json-extras.md)). Typed fields for what the gateway reads, `extras: JsonValue.Object` at each level for the rest, in order. Numbers stay JSON text. Text-carrying types override `toString`.
- **JSON.** Every body is read through `JsonMapper.exactTreeReader()` and `readTreeOrNull` (`JsonTrees.kt`): floats stay `BigDecimal`, trailing zeros stay, one value only, and an unreadable body is `null`. The conversion to and from `JsonValue` is by hand. An exponent keeps its value, not its spelling: `1e-5` goes out as `0.00001`, `1e2` as `1E+2`, on both adapters ([gotcha](../gotchas/json-number-literals-normalise-through-big-decimal.md)).
- **The call** (`OpenAiChatAdapter.complete`). `OpenAiRequestWriter` builds the body with `model` from the deployment, then extras, dropping `llmgw` from the request and from each message (ADR-020). WebClient posts it with `Authorization: Bearer <configured key>` and `X-Client-Request-Id: <gateway request ID>`, `exchangeToMono { toEntity(ByteArray) }` reads every status on one path, and one `Mono.timeout(request-timeout)` bounds the whole call. No other client header is forwarded.
- **The result** ([patterns/upstream-bytes-then-pure-classification](../patterns/upstream-bytes-then-pure-classification.md)). A readable 2xx goes through `OpenAiResponseReader`; malformed `usage` counts as omitted, so a paid answer is not thrown away. An unreadable 2xx is `UpstreamError`. Other statuses go to `OpenAiFailureClassifier`, which reads only `code`, `type` and `param` and checks them against the section 4 regexes. A usage whose total would not fit a `Long` counts as omitted. The provider's `Content-Type` is dropped before the body is read, so a value that cannot be parsed changes nothing.
- **Transport failures** (`TransportFailures`, shared by both adapters, in this order):
  1. A top-level `TimeoutException`, our `Mono.timeout`: `UpstreamTimeout`.
  2. `WebClientRequestException` whose cause chain says nothing was sent (refused or unreachable, unknown host, a TLS handshake that failed, pool acquire timeout or full queue): `ProviderUnavailable(null)`. A peer that closes during the handshake raises a closed-channel exception, which a close after the write raises too, so it falls to step 3 ([gotcha](../gotchas/tls-peer-close-during-handshake-is-a-closed-channel-exception.md)).
  3. Any other `WebClientRequestException`: `UpstreamError`. The provider may have the call, and may bill it, so RTE-02 must not repeat it.
  4. `IOException` (with `PrematureCloseException`), `DataBufferLimitException`, `DecodingException`, `WebClientResponseException`: `UpstreamError`.
  5. Anything else rethrows: a bug, so a 500. The adapter catches named types only.

  Any error from a response's body becomes `UpstreamBodyFailure`, a stackless `IOException` keeping only the class name for the log, on the stream and non-stream reads: nothing of ours runs above it, and Netty raises bad chunked framing as bare runtime exceptions ([bug](../bugs/adapter-broken-chunked-framing-raised-as-a-bug.md)). So bad framing is 502 before commit, an `upstream_error` frame after it, and silent in the drain.

  Mid-body through `toDataBuffers()`, measured: a close before the terminating chunk (`disconnect`) raises `PrematureCloseException`, a reset a bare `SocketException`, all three deadlines a top-level `TimeoutException`; a closed port on a stream is `WebClientRequestException`.

  Measured through WebClient 7.0.10 against the mock: a closed port and a full pool raise `WebClientRequestException`, `hang` past the deadline a top-level `TimeoutException`, `disconnect` after the headers a bare `PrematureCloseException`, a response over the limit a bare `DataBufferLimitException`. Against a raw socket (`RawProviderSocketIntegrationTest`): a reset after the write, a reply that is not HTTP and headers over 8 KB raise `WebClientRequestException` with no "nothing sent" cause, so all are 502; a provider `Content-Type` that cannot be parsed raised `InvalidMediaTypeException` from the body read until the adapter dropped the header.
- **Streams.** `ChatModelPort.stream` is a cold `Flow<ProviderStreamEvent>`: chunks, then one terminal event, with an expected failure a value at any position ([patterns/cold-event-flow-commits-at-first-frame](../patterns/cold-event-flow-commits-at-first-frame.md)). `OpenAiChatStream` makes the same POST with `Accept: text/event-stream`, `stream: true` and `include_usage: true`, whatever the client asked. Each `DataBuffer` is copied and released in the operator that receives it ([patterns/copy-and-release-pooled-buffers-before-a-flow](../patterns/copy-and-release-pooled-buffers-before-a-flow.md)), then `SseEventParser` (bytes, WHATWG, CR and BOM included) and `OpenAiChunkReader` feed `OpenAiStreamTranslator`, one per stream. All of this but the chunk reader runs in `SseStreamCall` and `StreamLifecycle`, so the Anthropic path shares it. A typed field holds only a value of its type, so presence and `null` survive in `extras`. One `Flux.timeout(Mono.delay(first), { Mono.delay(next) })` gives first-byte, idle and total from the pure `StreamDeadlines`, and a 1 s drain after `[DONE]`, so a connection returns to the pool (`Flux.timeout` takes publishers, not durations). `StreamTally` in core marks `Started`, forwards or drops the usage chunk, synthesises one from character counts when the provider omitted it and the client asked (`llmgw`, `ChatExtensions.MEMBER`), and reports `StreamSummary` once. `ChatStreamFrames` sets the commit headers at `Started` on the still-uncommitted response; a `Failed` before it is thrown, so `ChannelSendOperator` bypasses the write and the mapper writes a status; after it, a frame and a normal end. `SseBodyInserter` writes one flushed frame per element through `asFlux(context)` with the handler's context minus its `Job`, so `RequestContext` and MDC hold, also in the `finally` of a cancelled flow.
- **Back-pressure.** Demand runs end to end: `MonoSendMany` 128 buffers unconfirmed, `sendGroups` 32 frames, `asFlux` suspends at zero demand, `asFlow().buffer(8)`, then `FluxReceive` turns `autoRead` off. Per stream about 100 frames plus 8 upstream reads, read from source; measured on Windows loopback, the flow stopped at `chunks=152` on 16 KB frames and 464 on ordinary frames. `SlowClientStreamTest` proves a plateau under 4096 frames of 16 KB, not the figure. A client that stops reading meets `ClientStallHandler`, an `IdleStateHandler` with `observeOutput` off, ticking at a quarter of `client-write-timeout`. Its pure `StallClock` restarts the count on a completed write, a new first message in the `ChannelOutboundBuffer` or a change in `currentProgress()`: with bytes pending and none of these for that long it closes the channel, 1 to 1.5 timeouts after the last progress, and the normal cancel path runs (`StallClockTest`, `StalledClientStreamTest`). A frame joining the queue is not progress, so a provider that keeps sending does not delay the cut: a stopped client on one 16 KB frame every 200 ms is cut in 1.6 s at a 1 s timeout on Windows. `doOnConnection` installs one handler per HTTP request, which is all its state needs ([gotcha](../gotchas/reactor-netty-do-on-connection-runs-per-http-request.md)). Queue time does not count, and with nothing pending it never closes, so a slow provider is not a stall. Progress is seen only as the kernel takes bytes, so the connection, and only the connection, is safe down to one kernel step per timeout. On Windows loopback, at a 1 s timeout with idle 60 s, 85.6 KB/s held and 70.8 KB/s was cut; at the 30 s default the edge is 2 to 3 KB/s, and which side a client lands on varies with its buffer. This applies to ordinary frames too: a token stream has no backlog only for a client above the provider's rate, and a 984 B/s client on a 13 KB/s stream had 40888 bytes pending when it was cut at 76.8 s, while 2.9 KB/s completed.
- **A slow reader and `idle-timeout`.** Above the stall limit a slow reader can still lose the stream: `Flux.timeout` cannot see demand, so a live client too slow to pull an upstream read within `stream.idle-timeout` ends on it (`StreamStarvedUpstreamTest`). At the defaults that means below about 11.8 to 19.7 KB/s on 16 KB frames, a bracket measured on Windows loopback; the edge scales with frame size, by inference, since the demand refill of about 64 frames must drain inside `idle-timeout`. It moves with `idle-timeout`: at 2 s, 146 KB/s got the frame, so "160 KB/s held" is true only with a larger idle. The client gets an `upstream_timeout` frame, and an ERROR `Stream failed` and the adapter's WARN blame a healthy provider. It learns late, behind the backlog: at 7.9 KB/s the server failed at 106 s and the frame arrived at 305 s. RTE-02 must not count such a failure against the provider; GW-08 is the fix ([gotcha](../gotchas/client-stall-handler-moves-slow-readers-onto-idle-timeout.md)).
- **Disconnect.** Mid-stream, `MonoSendMany`'s `closeFuture` listener cancels its source and completes the write `Mono` normally, so `onErrorResume` sees nothing ([gotcha](../gotchas/reactor-netty-close-completes-the-write-mono-normally.md)); before the first frame, `ChannelOperations.terminate` cancels the chain. A first frame between the two fails at once, and `ChannelSendOperator` keeps its source, so `SseBodyInserter` ends the flow itself: `takeUntilOther` on a sink that `doFinally` fires ([bug](../bugs/first-frame-on-a-closing-channel-leaves-the-stream-flow-running.md), `ChatStreamClosingChannelTest`). The flow's cancellation reaches the upstream `Flux`, and `FluxReceive` closes the connection. One INFO `Stream cancelled` line carries the request ID. `ChatStreamLog` also gives DEBUG `Stream completed` and ERROR `Stream failed` (after commit only).
- **Anthropic: the request** ([patterns/member-policy-table-for-a-foreign-provider](../patterns/member-policy-table-for-a-foreign-provider.md), ADR-GW-03-005, ADR-GW-03-017). `AnthropicMemberPolicy` is a `Map<String, MemberRule>`: `Translated`, `Forward`, `Ignore`, `IgnoreWhen` (a default value counts as absent, numerically, so `0.0` is `0`), `Reject`; anything unlisted is `unsupported_parameter`. `AnthropicRequestWriter` reads `extras` directly, since no core policy needs those members, and gives `WrittenRequest.Body`, or `Refused` with the first refusal `Refusals` collected, before any I/O. A refused call is `ProviderResult.Failed`, or one `Failed` event, so a status with no socket touched. A translated member's value is checked by its writer: `stop`, `user` and `parallel_tool_calls` of another type are `unsupported_value`. `POST {base-url}/messages` carries `x-api-key`, `anthropic-version` and `X-Client-Request-Id`; `max_tokens` comes from the client or `default-max-tokens`; sampling goes only when sent; `user` or `safety_identifier` goes as its SHA-256 in `metadata.user_id`.
- **Anthropic: messages and tools** (ADR-GW-03-015, ADR-GW-03-016). `AnthropicConversationWriter` hoists `system` and `developer` to `system`, merges a run of `tool` messages and the `user` message after it with every `tool_result` first, and writes an assistant message as thinking blocks, text, then `tool_use`. `AnthropicToolWriter` maps `tools`, `tool_choice` and `parallel_tool_calls`. A forced `tool_choice` goes upstream on every model, and a provider 400 is relayed: there is no per-model table.
- **Anthropic: the reply** (`AnthropicResponseReader`, `AnthropicUsageReader`, ADR-GW-03-008, ADR-GW-03-010). Text blocks concatenate into `content`, `tool_use` blocks become `tool_calls`, and stop reasons map to `finish_reason`, with `pause_turn` and `model_context_window_exceeded` as `length`, `refusal` as `content_filter`, and an unknown one as `stop` with a WARN. `inputTokens` sums input, cache read and cache creation; the detail objects go in `Usage.extras` in the OpenAI shape, with `usage.cache_creation_input_tokens` as an extension. A missing or unreadable count, a `cache_*` one included, is omitted usage, so estimated and flagged; an absent or null cache count is 0 (ADR-GW-03-022).
- **Anthropic: the stream** (`AnthropicStreamDecoder`, ADR-GW-03-007, ADR-GW-03-012). `message_start` holds `id`, `model` and the input counts, and emits nothing; its `output_tokens` is a placeholder and is not read. The first text or tool delta is the first chunk and carries `role`, so an `overloaded_error` before it is a 503, not a frame. Tool indexes are renumbered from 0, an empty `partial_json` gives no chunk, and a tool with no arguments sent ends with `{}`. `message_delta` gives the finish chunk; `message_stop` the usage chunk and `Completed`, then the 1 s drain. `message_stop` with no `stop_reason` finishes `stop` (ADR-GW-03-021). The gateway writes its own `[DONE]`.
- **Thinking** (ADR-GW-03-011, ADR-GW-03-023). Thinking is on by default on most current models, and a tool turn must pass its blocks back. Blocks never enter `content`: a reply carries them in `message.llmgw.thinking_blocks`, a stream in the finish chunk's `delta.llmgw.thinking_blocks`. `HeldThinking` assembles them, and past `max-event-size`, open blocks counted, it drops them all with one WARN and the answer goes on. An assistant message echoing them is written with those blocks first, each cut to its type's allow-list; a block of another type is a 400. `llmgw` with no member left after nulls is absent. The gateway keeps no state between requests.
- **`warmUp()`** runs from each adapter's bean method, at startup, and does what the first requests would otherwise do on an event loop: `ReactiveFlowKt`'s `ServiceLoader` read, Jackson's first tree read and write, `HttpClient.warmup()`, and on Anthropic the SHA-256 digest. The tree read and write use Boot's `JsonMapper`, which `ChatHandler` shares.
- **The pool.** One named `ConnectionProvider` per adapter (`UpstreamClient`), so one provider's stall cannot exhaust the other's, HTTP/1.1, `disableRetry(true)` (Reactor Netty otherwise repeats a request once on some connection resets; keep it, as no test can go red without it: JDK NIO reports "Connection reset", which Netty's retry condition does not match; so a provider that closes a pooled connection without `Connection: close` costs the next client a 502, [gotcha](../gotchas/pooled-connection-closed-without-connection-close-costs-a-502.md)), `pendingAcquireMaxCount` twice `max-connections`, eviction every 30 s. `close()` disposes it. The client's event loops (`reactor-http-*`) are not the server's (`webflux-http-*`), so a response crosses threads once.
- **Usage.** `ChatCompletionService` keeps the provider's `Usage`, or asks `UsageEstimator` (length over 4 per text, 3 per message, 3 for the reply; an opaque part counts 0). `ChatHandler` adds `x-gateway-usage-estimated: true`; the body stays OpenAI-shaped. It writes bytes, not a tree, because `JacksonJsonEncoder` logs the value it encodes.
- **Exposure.** A team key is the control ([auth-and-teams](auth-and-teams.md)): a request reaches an adapter only after `AuthWebFilter`, and `ChatCall.team` is not forwarded to a provider. `server.address` defaults to `127.0.0.1`, and a non-loopback bind is not refused; TLS is the edge proxy's (ADR-GW-04-018). A CORS preflight under `/v1` is a 401 with no `Access-Control-*` header, so a browser does not send the JSON POST.
- **What typed members change** (GW-01 section 4, "Narrower than OpenAI"). Request: an absent `content` goes upstream as `"content":null`. Response: an absent `content` or `finish_reason` becomes `null`, a `finish_reason` that is not a string becomes `null`, an `index` that is not an integer becomes `0`. Both ways: a number keeps its value, not its spelling (`1e5` becomes `1E+5`), and `-0.0` becomes `0.0`. `ChatRequestReaderTest`, `OpenAiResponseReaderTest`, `ChatCompletionsEndToEndTest`.

## Embeddings

`POST /v1/embeddings` answers as OpenAI does (GW-05). `EmbeddingHandler` reads the body, `EmbeddingService` resolves the deployment and calls `EmbeddingModelPort`, and `RoutingEmbeddingModelPort` holds only OpenAI: a model on a provider with no embeddings is 400 `unsupported_value`, from the absence of a port (ADR-GW-05-003).

- **Adapter** (ADR-GW-05-002). `OpenAiEmbeddingAdapter`, with its own `UpstreamClient` and pool `embeddings-openai`, and a limit 16 times chat's. `encoding_format` and every other extra are forwarded as they came (ADR-GW-05-004).
- **Reply scan** (ADR-GW-05-005). The exception to "every body is read through `exactTreeReader`": `JsonMembers` walks one parser and copies each vector's byte range into `RawJson`. Small members go through the tree on their slice. Only `.json` uses the streaming API.
- **Lane** (ADR-GW-05-012). `CpuLane`, owned by the adapter and lent to the handler through `EmbeddingCpuPort`, runs the parse and typing, the upstream write, the reply's copy to an array, the scan and the error read, each with a deadline after `subscribeOn`. A counter refuses only the parse, past `cpu-threads` plus `cpu-queue-size`; later stages count towards it, are never refused for it, and are bounded by the in-flight budget, since each call holds a reservation. In the adapter a `RejectedExecutionException` is a closed lane, so shutdown only. The embedding path decodes to a joined `DataBuffer` and `CpuLane.copy` makes the array: exactly one of the copy and a cancel takes the buffer and releases it. Chat keeps `ByteArrayDecoder`.
- **Budget** (ADR-GW-05-011). `EmbeddingAdmission` reserves twice the body before the parse and the priced reply after typing, from the one `EmbeddingReplyBudget`; `ReplyHold` holds both to the end of the write, and `EmbeddingReplyFilter`'s `doFinally` ends it. No queue. Unset, `max-in-flight-bytes` is 25% of the heap. Heap in flight is at most 2 x the budget, so half the heap at the default; the other half holds chat, the JVM and at most `cpu-threads` running parse trees, which no reservation counts. All of that is arithmetic: no reply over 35 MB has run.
- **Write** (ADR-GW-05-013). `EmbeddingSlicedBody` sets `Content-Length` and writes 1 MiB views of the one array, one flushed group each. On a reply of more than one slice `ReplyWritePacer` holds each slice until the channel is writable, because neither `writeWith` nor `writeAndFlushWith` stops at an unwritable channel. The source runs on the channel's event loop, where a send writes inline.

## Failure behaviour

Fail-closed: there is no answer to give.

- Provider slow: `request-timeout` (300 s) bounds the whole call, then 504 `upstream_timeout`; the subscription is cancelled, so the connection closes.
- Provider down: connect 5 s, TLS handshake 10 s, DNS query 5 s, pool acquire 5 s, each 503 `provider_unavailable`. Nothing was sent, so a fallback may repeat the call. A peer that closes during the handshake is the exception: 502 `upstream_error`, and RTE-02 will not fall back on it.
- Connection reset or closed after the write, a reply that is not HTTP, headers over 8 KB: 502 `upstream_error`. The provider may have the call.
- Provider 401 or 403: 502 `upstream_auth_failed` with `x-should-retry: false`; the client's key is not the problem.
- Provider quota: 503 `upstream_quota_exhausted` with `x-should-retry: false`.
- Client disconnects: the coroutine, the Mono and the upstream connection are cancelled. The provider may still bill the partial call; COST-02 owns that. `StreamSummary` holds what is known of a stream.
- Provider silent on a stream: `stream.first-byte-timeout` (120 s) gives 504 `upstream_timeout` before commit; `stream.idle-timeout` (60 s) and `stream.total-timeout` (30 m) give 504 before commit, an `upstream_timeout` frame after it. A provider that holds the body open after `[DONE]` costs at most the 1 s drain, silently, and that connection closes instead of returning to the pool.
- 2xx with no chunk, or a first event that cannot be read: 502 `upstream_error` before commit. An in-band error first: the mapped row, by status.
- Provider closes without `[DONE]`: complete if a `finish_reason` was seen, and the gateway writes `[DONE]`; otherwise `upstream_error`. Anthropic the same, with `message_stop` and `stop_reason`.
- A member the provider cannot honour: 400 `unsupported_parameter`, `unsupported_value` or `invalid_request`, with `param` when it passes the regex, and no upstream call. RTE-02 may try another deployment.
- Anthropic `event: error` before the first chunk: the row's real status by `error.type`, and an in-band `ProviderUnavailable` means the provider took the request, unlike a transport 503. After it: a frame.
- Anthropic 529: 503 `provider_unavailable`. A spend-cap 429 (`enforced_spend_limit_reached`) and 402: 503 `upstream_quota_exhausted`, `x-should-retry: false`. `timeout_error` on any status: 504. A 404 of Anthropic's shape: `model_not_found`, otherwise 502. An operator's own spend limit is a 400 marked only by its message, so it reaches clients as `upstream_rejected_request` (ADR-GW-03-013).
- Held thinking blocks over `max-event-size`: dropped, one WARN, and the answer proceeds.
- Malformed event, in-band error, reset, premature close, or an event over `stream.max-event-size` after commit: one error frame, no `[DONE]`, a clean end; the rest is not read. The provider's in-band `message` is never relayed.
- Client slow: back-pressure to the provider, and nothing is dropped above the limit of `idle-timeout`, about 11.8 to 19.7 KB/s at the defaults on 16 KB frames. Below it the stream ends with an `upstream_timeout` frame, behind the backlog, with an ERROR `Stream failed` and the adapter's WARN against a healthy provider (How it works).
- Client stops reading: bytes pending and no write progress for `client-write-timeout`, however many frames the provider still sends, so the connection closes and the stream ends `cancelled`, with one INFO from `ClientStallHandler` carrying the connection ID and no request ID: on a stream `Stream cancelled` follows and the two share no key, and a non-stream cut leaves only that line (OBS-03). A stream that fits the queues ends first: `completed` means handed to Netty, not read by the client, so a stalled client can be logged `Stream completed` (DEBUG) while it lost the tail; the provider did finish, so usage is right (smoke finding 3).
- A bug in the flow after commit: one ERROR with the stack trace, `internal_error` frame, clean end. Only what the flow cannot catch reaches the mapper's committed branch.
- Embeddings budget full, lane queue full at the parse, lane closed, or the pool's pending queue full: 503 `gateway_overloaded` with `retry-after` and `retry-after-ms`, at once. Nothing goes upstream, and a bad body under a full budget gets this too; only a lane closed by shutdown can drop a call the provider may bill. One log line, no stack trace (ADR-GW-05-011). On chat the pool's pending limit is still `provider_unavailable` (GW-16).
- Embeddings stage past its deadline: 504 `upstream_timeout` in the adapter, 503 `gateway_overloaded` on the request's parse. A JVM-fatal error sends no signal, so the deadline ends the stage.
- Embeddings non-2xx body over 64 KiB: not read, the row for its status with no `code` or `param` (ADR-GW-05-014).
- Response over `max-response-size`: 502 `upstream_error`, never 413.
- Provider 2xx with an unreadable body: 502 `upstream_error`; the body is not logged.
- Provider usage missing or unreadable: estimated and flagged; the call succeeds.
- An enabled provider's key absent, or with a character outside visible ASCII such as a trailing newline: the app does not start. A disabled provider's values stop nothing.
- Graceful shutdown: Boot's default, up to 30 s per phase; a longer in-flight call is cut until OPS-03.

## Gotchas

- A send of a `Flux` runs up to 128 items past an unwritable channel, and `writeAndFlushWith` is the same send: only the source can pace a large body ([gotcha](../gotchas/reactor-netty-send-writes-its-whole-prefetch-past-unwritable.md)).
- A heap buffer is copied whole to direct memory on the event loop at write ([gotcha](../gotchas/netty-copies-a-heap-buffer-to-direct-on-write.md)).
- `jvm.buffer.memory.used{id=direct}` reads 0 through 33 MB replies, so direct memory needs NMT or Netty's metrics ([gotcha](../gotchas/jvm-direct-buffer-metric-misses-netty-pooled-memory.md)).
- The mock's float vectors are sparse, so its largest reply is about 35 MB and ADR-GW-05-006's 198 MiB has never run (OPS-06).
- `DataBufferLimitException` is the adapter's to translate: a bare one that reaches the HTTP edge is a 500. On the request side `readJsonObject` translates its own ([bugs/gateway-body-limit-on-functional-route-gives-500](../bugs/gateway-body-limit-on-functional-route-gives-500.md)).
- Wait with `Mono.timeout`, never `withTimeout`: its continuation lands on a thread BlockHound does not watch ([gotchas/spring-coroutine-handlers-resume-on-default-executor-after-delay](../gotchas/spring-coroutine-handlers-resume-on-default-executor-after-delay.md)).
- With `USE_BIG_DECIMAL_FOR_FLOATS`, a float past `BigDecimal`'s range (`1e99999999999`) raises a bare `NumberFormatException` quoting the literal, not a `JacksonException`, so a catch of `JacksonException` alone gives a client a 500 and puts the value in the log. Read through `readTreeOrNull`.
- Jackson builds its tree deserializer on first use under a `ReentrantLock`, and concurrent first requests park on it on an event loop; BlockHound fails that. `warmUp()` reads and writes a tree first. A new first-use path in another `JsonMapper` needs the same.
- `ReactorClientHttpConnector` implements `SmartLifecycle`, and `spring-webflux` declares `spring-context` optional, so the module depends on `spring-context` although it wires nothing.
- `HttpHeaders.getContentType()` throws `InvalidMediaTypeException` on an unparsable value; `readJsonObject` turns that into 415. WebTestClient refuses to send such a value, so the test uses a plain client.
- In the `integrationTest` suite `src/test/resources` is not on the classpath, so the suite has its own `application.properties` ([gotchas/integration-test-suite-has-no-test-resources](../gotchas/integration-test-suite-has-no-test-resources.md)).
- A `@DynamicPropertySource` wins over `@TestPropertySource`, and a superclass's runs last, so `ClosedProviderPortTest` cannot extend `MockBackedTest` and a subclass cannot change its key ([gotchas/dynamic-property-source-superclass-registers-last](../gotchas/dynamic-property-source-superclass-registers-last.md)).
- With `logging.level.web=TRACE`, Spring logs a `String` body in full, on the client side too. `NoLeakIntegrationTest` shares its JVM and log with its own clients, so `MockBackedTest` sends and reads bytes.
- A non-stream client disconnect leaves no gateway log line with the request ID, and the WARNs from `FluxReceive` and `HttpClientConnect` carry none, so a call the provider may bill cannot be found from the gateway log alone (OBS-03, COST-02). A stream has its `Stream cancelled` line.
- A client RST leaves `FluxReceive`'s WARN `An exception has been observed post termination`, with the peer port and no request ID; a true FIN does not, and a socket closed with unread bytes sends RST, so most busy-stream disconnects do (smoke finding 4). It remains: silencing the logger would hide real errors. `Stream cancelled` gives the ID, and matching the two by connection is OBS-03's.
- An HTTP/1.0 client gets `HTTP/1.1 200 OK` with `transfer-encoding: chunked` and `connection: close`, which it cannot decode: Reactor Netty's behaviour (smoke finding 6).
- A client that half-closes (`shutdown(SHUT_WR)`) and keeps reading is treated as gone: `client_cancelled` within 17 ms. Reactor Netty's default (smoke finding 7).
- `ClientStallHandler` spares a slow reader, and `idle-timeout` then ends it with an `upstream_timeout` for a healthy provider ([gotchas/client-stall-handler-moves-slow-readers-onto-idle-timeout](../gotchas/client-stall-handler-moves-slow-readers-onto-idle-timeout.md)).
- A chunk with empty `choices` and no `usage` is forwarded with its extras; only the one carrying `usage` is dropped for a client that did not ask.
- `Flux.timeout(Publisher, Function)` has no `Duration` form with a factory: both arguments are publishers, so each item schedules a `Mono.delay` on `parallel`.
- Inside `Socket().apply { }`, `port` is the socket's own, 0: an integration test hits `BindException`.
