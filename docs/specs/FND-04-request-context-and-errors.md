# FND-04: Request context and error model

## 1. Context and goal

Every later item needs two things on day one: a request ID that ties a response, a log line, a span (OBS-01) and a ledger row (COST-02) to one call, and one error shape. Without them GW-01 would invent its own error bodies, GW-04's auth filter would fail outside any controller advice, and RL-01 and GRD-01 would each pick their own status and code. Clients would see Spring Boot's default error JSON on some paths and something else on others.

FND-04 builds both. The request ID is generated by the gateway for every request and returned in `x-request-id`, the header OpenAI itself returns and its SDKs already read. Expected failures become a sealed `GatewayError` type in `gateway-core`, and one table there gives each one its HTTP status and OpenAI error fields. One `WebExceptionHandler` in `gateway-app` turns everything that escapes a request into the OpenAI envelope `{"error":{"message","type","param","code"}}`: framework errors (404, 405, 406, 413, 415, malformed JSON), errors raised by filters and handlers, and bugs (500, with no exception message in the body).

It serves pillar 1 (drop-in: the same status codes, envelope and request-ID header an OpenAI client already handles) and pillar 4 (accountable: the request ID is the key the cost ledger is idempotent on). It adds no product endpoint. That is GW-01's job.

## 4. Contract

### Headers

| Header | Direction | Value | Notes |
|---|---|---|---|
| `x-request-id` | response, on every response WebFlux handles: 2xx, 4xx, 5xx, actuator, unknown routes | UUIDv7, canonical lowercase hex-and-dash, 36 characters (ADR-FND-04-002) | OpenAI's own response header ("Unique identifier for this API request"). openai-python fills `_request_id` and `APIStatusError.request_id` from it, so this is the OpenAI name rather than an `x-gateway-*` one (ADR-004 lists the request ID among header-borne features). A request's own `x-request-id` is ignored. Clients treat the value as opaque (RFC 9562 §6.12). |
| `x-client-request-id` | request, optional | 1 to 512 characters, each U+0020 to U+007E | OpenAI's `X-Client-Request-Id`: "only ASCII characters and be no more than 512 characters long; otherwise, the request will fail with a 400 error". Here, a value outside the range, or the header repeated, gives 400 `invalid_client_request_id`. An empty value counts as absent. |
| `x-client-request-id` | response | the accepted value, echoed | Extension: OpenAI documents no echo. Present only when the request carried a valid one. |
| `allow` | response to 405 | allowed methods, comma-separated | RFC 9110 §15.5.6 requires it on 405. |

Responses that never reach WebFlux carry neither header nor envelope. Reactor Netty rejects these itself: a malformed request line, an initial line over `server.netty.max-initial-line-length` (4KB), or a header over `server.max-http-request-header-size` (8KB, applied per header by Netty).

### Error body

```json
{"error":{"message":"Unknown request URL.","type":"invalid_request_error","param":null,"code":"unknown_url"}}
```

- `Content-Type: application/json`. Never `application/problem+json` (ADR-FND-04-005).
- Exactly one top-level member, `error`, with exactly four members, always present. `message` and `type` are strings. `param` and `code` are strings or `null`. That is the shape openai-python reads: `body["error"]`, then `message`, `code`, `param`, `type`.
- `message` is for humans, in English. It never contains request content (bodies, query strings, header values other than the two IDs) or an exception message. A 5xx message ends with the request ID, as OpenAI's own 500 message does.
- `code` is the stable machine-readable discriminator. `type` is a coarse class that mirrors the value OpenAI's API returns for the equivalent condition. The HTTP status is what OpenAI SDKs map to exception classes: 400 `BadRequestError`, 401 `AuthenticationError`, 403 `PermissionDeniedError`, 404 `NotFoundError`, 409 `ConflictError`, 422 `UnprocessableEntityError`, 429 `RateLimitError`, ≥ 500 `InternalServerError`.
- **Stability rule:** once a (status, type, code) row ships it is never changed. A new condition gets a new code.
- 2026-11-04 (GW-04): the `unknown_url` message no longer quotes the method and path, and `message` holds no path. The (status, type, code) row is unchanged. ADR-GW-04-020; section 5's `UnknownRoute(method, path)` and `toGatewayError(method, path)` are the design as first built.

### Implemented by FND-04

| Condition (raised by) | `GatewayError` variant | Status | `type` | `code` | `message` | Extra headers |
|---|---|---|---|---|---|---|
| Handler or filter raises it | `InvalidRequest(message, code, param)` | 400 | `invalid_request_error` | the variant's | the variant's | – |
| Body not JSON or not the expected shape (`ServerWebInputException` caused by `DecodingException`) | `InvalidRequest` | 400 | `invalid_request_error` | `invalid_body` | `The request body could not be read as JSON of the expected shape.` | – |
| Other `ServerWebInputException` (missing or mistyped value) | `InvalidRequest` | 400 | `invalid_request_error` | `invalid_request` | `The request is missing a required value or has a value of the wrong type.` | – |
| Bad `x-client-request-id` (`RequestContextWebFilter`) | `InvalidRequest` | 400 | `invalid_request_error` | `invalid_client_request_id` | `The x-client-request-id header must be one value of 1 to 512 printable ASCII characters.` | – |
| No handler for the path | `UnknownRoute` | 404 | `invalid_request_error` | `unknown_url` | `Unknown request URL.` | – |
| Path matched, method not | `MethodNotAllowed(method, allowed)` | 405 | `invalid_request_error` | `method_not_allowed` | `Method <METHOD> is not allowed for this URL.` | `allow` |
| `Accept` cannot be met | `NotAcceptable` | 406 | `invalid_request_error` | `not_acceptable` | `None of the media types in the Accept header can be produced by this endpoint.` | – |
| Body over the codec limit (`ContentTooLargeException`, or a `ServerWebInputException` with `DataBufferLimitException` in its cause chain) | `ContentTooLarge` | 413 | `invalid_request_error` | `request_too_large` | `The request body is larger than this endpoint accepts.` | – |
| Content-Type not readable | `UnsupportedMediaType` | 415 | `invalid_request_error` | `unsupported_media_type` | `The request Content-Type is not supported by this endpoint.` | – |
| Any other framework 4xx (`ErrorResponse` with status 400-499 not listed above) | `RejectedRequest(status)` | that status | `invalid_request_error` | `null` | `The request was rejected with HTTP status <status>.` | – |
| Anything else: bugs, non-gateway 5xx, a timeout an adapter did not translate | `Internal` | 500 | `server_error` | `internal_error` | `The gateway had an internal error. Include the request ID <id> if you report it.` | – |

`type` values: OpenAI returns `invalid_request_error` for request-level 4xx, including unknown URLs and unknown models, and `server_error` for its 500 (public reports cited in ADR-FND-04-004; OpenAI documents no enumeration of `type`). OpenAI's unknown-URL error has `code: null`. `unknown_url` is a gateway value in a field the shape declares as a free string.

### What stays OpenAI-compatible, what is an extension

- **Compatible:** status codes and the SDK exception classes they select, the envelope shape, `x-request-id`, and the `X-Client-Request-Id` rules (ASCII, ≤ 512, 400 when invalid).
- **Extensions:**
  - Non-null `code` values on errors OpenAI leaves `null` (unknown URL, 405, 406, 415).
  - The `x-client-request-id` echo.
  - The gateway's `code` values in the reserved table.
- **Narrower than OpenAI:** `x-client-request-id` excludes ASCII control characters, which OpenAI's wording ("ASCII characters") does not mention. HTTP already forbids most of them in field values.

## 5. Design

### Modules and ports

No port: FND-04 has no I/O capability to abstract. All pieces are plain types, a pure table, a filter and a handler.

**`gateway-core`** (first sources; packages `.gateway.core.request` and `.gateway.core.error`):

```kotlin
// .gateway.core.request
@JvmInline value class RequestId(val value: Uuid)          // kotlin.uuid.Uuid, stable since Kotlin 2.4
// toString() = canonical lowercase hex-and-dash.

class RequestIdGenerator(clock: java.time.Clock, random: kotlin.random.Random) {
    fun next(): RequestId                                   // UUIDv7, RFC 9562 §5.7
}

@JvmInline value class ClientRequestId private constructor(val value: String) {
    companion object {
        const val MAX_LENGTH = 512
        fun parseOrNull(raw: String): ClientRequestId?      // 1..512 chars, each U+0020..U+007E
    }
}

// .gateway.core.error
sealed interface GatewayError {
    data class InvalidRequest(val message: String, val code: String, val param: String? = null) : GatewayError
    data class UnknownRoute(val method: String, val path: String) : GatewayError
    data class MethodNotAllowed(val method: String, val allowed: Set<String>) : GatewayError
    data object NotAcceptable : GatewayError
    data object ContentTooLarge : GatewayError
    data object UnsupportedMediaType : GatewayError
    data class RejectedRequest(val status: Int) : GatewayError   // init: require(status in 400..499)
    data object Internal : GatewayError
}

data class ErrorReply(
    val status: Int,
    val message: String,
    val type: String,
    val param: String?,
    val code: String?,
    val headers: Map<String, String> = emptyMap(),          // lowercase names, e.g. "allow"
)

fun GatewayError.toReply(requestId: RequestId): ErrorReply  // the section 4 table, one exhaustive `when`
```

- The `type` and `code` strings are `const val`s in `object ErrorTypes` and `object ErrorCodes`, so tests and later items share one spelling.
- `RequestIdGenerator.next()` reads `clock.millis()` once and draws 10 random bytes. It sets version 7 and variant `0b10`, and builds the ID with `Uuid.fromLongs`.
- A clock outside `0 until 2^48` ms is a bug: `check` fails with `IllegalStateException`, which becomes a 500.
- No monotonic counter within one millisecond. RFC 9562 §6.2 makes it optional, and nothing here sorts IDs within a millisecond.
- KDoc on `InvalidRequest.message`: client-safe, never contains request content.

`RequestContextWebFilter`, per request:
1. Generate the ID.
2. Set the `x-request-id` response header.
3. Store the ID in the exchange attribute.
4. Validate `x-client-request-id`. When invalid, throw `GatewayErrorException(InvalidRequest(...))`.
5. Echo a valid client ID.
6. Run `withContext(RequestContext(...) + MDCContext(MDC map + ids)) { chain.filter(exchange) }`.

`RequestContextConfiguration` beans:
- `Clock.systemUTC()`.
- `RequestIdGenerator(clock, random)`, where `random` is `SecureRandom.getInstance("DRBG")`, called once in the bean method so seeding happens at startup, wrapped with `asKotlinRandom()`.
- The filter.

`Throwable.toGatewayError(method, path)` handles, in order:
1. A `GatewayErrorException` gives its own `error`.
2. A `ServerWebInputException` with a `DataBufferLimitException` in its cause chain gives `ContentTooLarge`: only the request-body read path means the client sent too much. A `DataBufferLimitException` anywhere else (an upstream response, say) is `Internal`; adapters translate their own.
3. Any `org.springframework.web.ErrorResponse` is dispatched on its status: 400 (`invalid_body` when the cause chain holds a `DecodingException`, else `invalid_request`), 404, 405 (allowed methods from `MethodNotAllowedException.supportedMethods`), 406, 413, 415, any other 4xx as `RejectedRequest(status)`, and 5xx as `Internal`.
4. Everything else gives `Internal`.

`GatewayErrorWebExceptionHandler.handle`, in order:
1. If the response is already committed, log at ERROR with the request ID and return `Mono.error(CommittedResponseAbort(requestId))`, a stackless stand-in, so the connection is closed and no checkpoint reaches Reactor Netty's log. `DisconnectedClientHelper.isClientDisconnectedException` is not asked about the original exception: it matches phrases such as "broken pipe" anywhere in the cause chain's messages ([bug](../knowledge/bugs/error-mapper-disconnect-check-turns-errors-into-empty-200.md)).
2. Otherwise always write the envelope, whatever the exception looks like.
3. Translate the exception and call `toReply(requestId)`. The request ID comes from the exchange attribute; if the filter never ran, one is generated here.
4. Write the reply: set the status, set `Content-Type: application/json` and the reply headers, set `x-request-id` again, and write the DTO with the first `HttpMessageWriter` in `codecs.writers` that can write it as `application/json`.
5. If writing fails, write a constant pre-serialized 500 envelope instead. A write that fails because the client is gone (the helper accepts the failure) is logged at DEBUG and completes.
6. After the write, log 5xx at ERROR with the stack trace and 4xx at DEBUG (status, code, request ID; no exception message). A 5xx is not logged at ERROR only when its write failed and the helper accepts that failure (step 5). The logged throwable is a copy without Reactor's assembly checkpoint, which Spring's `ExceptionHandlingWebHandler` attaches with the raw query string (`LoggableFailure`). Each log call runs inside `MDC.putCloseable("requestId", ...)`, because the mapper runs outside the coroutine.

Libraries:
- `kotlinx-coroutines-slf4j` (`MDCContext`) is new in `gateway-app`: catalog alias `kotlinx-coroutines-slf4j`, version from the coroutines BOM.
- Nothing is added to core: `kotlin.uuid` and `java.time` are already on its classpath.

### Failure model

| Event | Behaviour | Why |
|---|---|---|
| Client sends `x-request-id` | Ignored; a fresh ID is returned | The ID is the usage-event idempotency key (CLAUDE.md, Cost). A client-chosen value could repeat and suppress a billed event (ADR-FND-04-001). |
| Invalid or repeated `x-client-request-id` | 400 `invalid_client_request_id` (fail-closed) | Same behaviour as OpenAI. Keeps control characters out of logs. |
| Clock outside the UUIDv7 range | `IllegalStateException`, 500 | A configuration bug, not a client error. |
| DRBG seeding | Done once in the bean method at startup, off the event loop | `UUID.randomUUID()`'s default `NativePRNG` reads `/dev/urandom` per call, which BlockHound reports as blocking (spring-framework#24027). Verified 2026-11-03 under BlockHound on the event loop (section 11): the seeded DRBG blocks nowhere, so the fallback (a `java.util.SplittableRandom` seeded from `SecureRandom` once at startup; unique, not unguessable) is not used. |
| Exception from a filter, handler mapping, codec or handler, before commit | Envelope with the translated status | One mapper (ADR-FND-04-005). |
| Exception after the response is committed (a stream) | ERROR log with the request ID. A stackless `CommittedResponseAbort` replaces the error and Reactor Netty closes the connection, so the client sees a truncated response. | Status and headers are already sent. **Boundary for GW-02:** catch failures inside the `Flow` before they escape, emit an SSE error event whose payload is this envelope (same `toReply` and DTO), then end the stream. |
| Client disconnected | Before commit: the envelope is written as usual, and a write failure the helper attributes to the client is logged at DEBUG, not routed to the fallback; only then does a 5xx have no ERROR line. An exception that merely quotes a disconnect is logged at ERROR, because a write that succeeds proves the client was there. After commit: ERROR log and the stackless abort; nothing can confirm a disconnect there. | Not an error. Cancellation stays with the coroutine machinery: the mapper never sees a `CancellationException` from a client disconnect, because the request `Mono` is cancelled. A `TimeoutCancellationException` that reaches it means an adapter did not translate a timeout: 500 and ERROR. |
| The envelope cannot be serialized | Constant pre-serialized 500 envelope | The guarantee "every error is an envelope" does not depend on the codec. |
| Request rejected by Reactor Netty before WebFlux | Netty's own response, no envelope, no `x-request-id` | Outside the WebFlux chain; documented in section 4. |
| Provider, Redis, Postgres, broker | n/a: FND-04 calls none. Section 4 reserves their error rows. | |
| Timeouts and retries | None: no outbound call. OpenAI SDKs retry 408, 409, 429 and ≥ 500 twice by default. Later items use `retry-after` and `x-should-retry` to steer that. | |

### ADR-FND-04-001: Request ID header and origin
- **Context:** Every response needs an ID that support, logs, spans and the ledger share. CLAUDE.md (Cost) makes usage events idempotent by request ID, so the ID must be unique per call. OpenAI returns `x-request-id` on every response, and openai-python exposes it as `_request_id` and `APIStatusError.request_id`. OpenAI also accepts a client-chosen `X-Client-Request-Id` (ASCII, ≤ 512, else 400) for correlating requests whose response was lost, for example to a timeout.
- **Options considered:**
  - A) Accept a client `x-request-id` when present, generate one otherwise. This is the common proxy behaviour. Rejected: a client can repeat or forge a value, which breaks ledger idempotency (a second billed call dropped as a duplicate) and lets one team's traffic collide with another's in logs.
  - B) Always generate `x-request-id` and ignore the request's. Accept a separate, validated `x-client-request-id`, echo it, and log it.
  - C) B without any client ID. Rejected: the case OpenAI's header exists for (no response, nothing to quote) is real for a gateway client too. ADR-011's agent runtime could set it to its step ID at no cost.
  - D) A gateway-specific header (`x-gateway-request-id`). Rejected: OpenAI SDKs read `x-request-id` already; ADR-004 says a feature uses the OpenAI form when one exists.
- **Decision:** B. An invalid or repeated `x-client-request-id` gives 400, as OpenAI does. The accepted range is printable ASCII (U+0020 to U+007E), 1 to 512 characters.
- **Consequences:** COST-02 can key usage events on the request ID safely. Log lines and responses are tied by the ID. The 400 rule rejects a few values OpenAI might accept (tabs, other control characters), which is accepted for log hygiene. Buys: one trustworthy key across logs, spans and the ledger.
- **Date:** 2026-11-03

### ADR-FND-04-002: Request ID format and generator
- **Context:** The ID is opaque to clients (RFC 9562 §6.12), but it becomes a ledger key (COST-02) and appears in every log line. Kotlin 2.4 makes `kotlin.uuid.Uuid` stable; `Uuid.generateV7()` and `generateV7NonMonotonicAt()` are still `@ExperimentalUuidApi`. JDK 25 has no UUIDv7 factory: JDK-8334015 was under review in May 2025, and its release is unconfirmed. `UUID.randomUUID()` uses `NativePRNG`, which reads a file per call, and BlockHound reports that on an event loop (spring-framework#24027).
- **Options considered:**
  - A) UUIDv4 (`UUID.randomUUID()`). Rejected: random keys have poor index locality (RFC 9562 §2.1, §6.11) for the ledger, and the call blocks per BlockHound.
  - B) UUIDv7 via the experimental `Uuid.generateV7()`. Rejected: an experimental API on the hot path, with no injectable clock or random source, so it cannot be tested deterministically.
  - C) ULID. Rejected: not an IETF format, needs a library or its own codec, no native Postgres type.
  - D) An OpenAI-style prefixed string (`req_<32 hex>`). Rejected: cosmetic, and it needs stripping at every store boundary; a UUID maps straight onto a Postgres `uuid`.
  - E) UUIDv7 built in core by `RequestIdGenerator(clock, random)` from `clock.millis()` and 10 random bytes, wrapped in the stable `kotlin.uuid.Uuid`. The app injects `Clock.systemUTC()` and a DRBG `SecureRandom`, seeded at startup, as `kotlin.random.Random`. RFC 9562 §6.9: implementations "SHOULD utilize a cryptographically secure pseudorandom number generator".
- **Decision:** E, canonical lowercase hex-and-dash text. No intra-millisecond monotonic counter (RFC 9562 §6.2 makes it optional).
- **Consequences:** Generation is a pure function of the clock and the random source, so it is TDD'd in core and adds core coverage. Postgres can store the ID as `uuid` with time-ordered inserts. The creation millisecond is visible in the ID (RFC 9562 §8 calls this "a very small attack surface"); the response's own `created` field carries the same fact. Whether a seeded DRBG avoids per-call entropy reads is checked by the first BlockHound run, with the `SplittableRandom` fallback in section 5. Buys: testability (CLAUDE.md, injected clock) and index locality, with no experimental API.
- **Date:** 2026-11-03

### ADR-FND-04-003: Where the request context lives and how it reaches logs and spans
- **Context:** Code in a `suspend` handler, later the request pipeline, needs the request ID without threading the exchange through every call. Log lines need it in MDC. The exception mapper runs outside any coroutine. `CoWebFilter` stores `currentCoroutineContext().minusKey(Job)` in the exchange attribute `COROUTINE_CONTEXT_ATTRIBUTE` when it calls the chain, and that context is "passed to `InvocableHandlerMethod`" for `suspend` handlers (Spring Framework 7 source). `MDCContext` (kotlinx-coroutines-slf4j) reinstalls a captured MDC map on every resume, but "you cannot update MDC context from inside the coroutine simply using MDC.put". Spring's `PropagationContextElement` with Micrometer context propagation is the documented path for tracing context in coroutines; it needs `io.micrometer:context-propagation` and `Hooks.enableAutomaticContextPropagation()`.
- **Options considered:**
  - A) A `RequestContext` coroutine element in **core**, read implicitly by core code. Rejected: core functions would depend on an invisible ambient value, which makes pure policies harder to test. Core receives `RequestId` explicitly where it needs one (usage events).
  - B) `RequestId` type in core. `RequestContext` element in the app, installed by the first `CoWebFilter` together with `MDCContext`, and mirrored in an exchange attribute for non-coroutine code (the mapper).
  - C) Micrometer context propagation now: a `ThreadLocalAccessor` for the MDC keys, `spring.reactor.context-propagation=auto` and `PropagationContextElement`. One mechanism for Reactor and coroutine code. Rejected for FND-04: no Reactor-operator code logs yet. It adds a dependency and per-operator overhead before anything needs it, and it is the mechanism OBS-01 brings for `traceId`/`spanId` anyway.
  - D) No context: pass the exchange or the ID as a parameter everywhere and skip MDC. Rejected: every log call site must remember the ID.
- **Decision:** B. The trace ID is never used as, or derived from, the request ID. A `traceparent` identifies a whole trace, may be client-chosen or restarted (W3C Trace Context §3.2.2.3, §3.4), and spans many requests in an agent run (ADR-011). OBS-01 records the request ID on the server span as `http.response.header.x-request-id`.
- **Consequences:** `suspend` handlers and code they call read `currentCoroutineContext()[RequestContext]`. MDC is correct in coroutine code and in the mapper, but not in Reactor callbacks of future adapters until OBS-01 adds context propagation (noted for OBS-01). Functional `coRouter` endpoints, if GW-01 chooses them, must be checked for the same attribute-based propagation (unverified here). Buys: core stays explicit and pure; one cheap filter gives every log line the ID.
- **Date:** 2026-11-03

### ADR-FND-04-004: Error model in core and how far FND-04 goes
- **Context:**
  - CLAUDE.md: "Expected failures are sealed result types in core ... The app maps both to the OpenAI error envelope in one place."
  - OpenAI documents the error codes by status but no enumeration of `type`. Public bodies show `invalid_request_error` for invalid keys (401), unknown models and unknown URLs (404), `server_error` for 500, and `requests` / `tokens` / `tokens_usage_based` for 429, with `code: rate_limit_exceeded`. The `type` varies, so clients cannot rely on it.
  - openai-python reads `code`, `param` and `type` from `body["error"]` and picks the exception class by status.
  - Anthropic's API uses one `type` per status (`authentication_error`, `permission_error`, `not_found_error`, `rate_limit_error`, `api_error`, ...).
- **Options considered:**
  - Where the table lives:
    - T1) Core: `GatewayError.toReply(requestId)` gives status (a plain `Int`), type, code, message and headers.
    - T2) Core holds the errors; the app holds the status/type table. Rejected: the triple is one contract (ADR-004). Splitting it lets status and code drift, and the table would be tested only through Spring.
  - Which `type` values:
    - Y1) Mirror OpenAI's value for the equivalent condition; `code` is the stable discriminator.
    - Y2) Anthropic-style, one type per status. Rejected: a client written against OpenAI that inspects `type` would see values OpenAI never sends for the same status.
  - How many variants now:
    - V1) All variants the roadmap will need, with guessed payloads. Rejected: `RateLimited` needs RL-01's limit headers, `GuardrailBlocked` GRD-01's rule data, and the upstream errors GW-01's provider data. Guessed fields would be rewritten.
    - V2) Only what FND-04's mapper produces now, plus a reserved status/type/code table in the spec and ADR-015.
  - Message ownership:
    - M1) Fixed messages per variant in core; caller-supplied only for `InvalidRequest`, which carries a KDoc constraint.
    - M2) Exception messages passed through. Rejected: they leak internals and can echo request bytes.
- **Decision:** T1, Y1, V2, M1. 5xx messages end with the request ID, as OpenAI's 500 does. `toReply` is one exhaustive `when`, so a new variant does not compile until it has a row. Codes never change once shipped.
- **Consequences:** HTTP status integers live in core as data; no HTTP library is imported. Later items extend one sealed type and one table and add one test row each. A non-gateway 5xx from the framework is reported as 500 `internal_error`, because only gateway variants may produce 502, 503 or 504. Buys: one reviewable table, unit-tested without Spring; the compiler enforces a mapping for every variant.
- **Date:** 2026-11-03

### ADR-FND-04-005: One mapper
- **Context:**
  - Errors arise in four places: WebFilters (GW-04's auth filter, this item's client-ID check), handler mapping (404, 405, 406, 415), codecs (400, 413) and handlers.
  - `@ExceptionHandler` / `@ControllerAdvice` handle "exceptions from controller methods". Through `DispatchExceptionHandler`, the `RequestMappingHandlerAdapter` also applies them to errors "before a handler is mapped". They do not cover functional endpoints or errors outside `DispatcherHandler`.
  - A `WebExceptionHandler` handles "exceptions from the chain of WebFilter instances and the target WebHandler".
  - Boot registers `DefaultErrorWebExceptionHandler` at `@Order(-1)` under `@ConditionalOnMissingBean(ErrorWebExceptionHandler, search = CURRENT)`, and its body has `timestamp`, `path`, `status` and `error`.
  - RFC 9457 problem details (`application/problem+json`) can be switched on with `spring.webflux.problemdetails.enabled`. RFC 9457 §4 itself says problem details are "not to replace existing domain-specific formats".
- **Options considered:**
  - A) `@RestControllerAdvice` (or `ResponseEntityExceptionHandler`) for controller errors, plus Boot's handler customized through `ErrorAttributes` for the rest. Rejected: two mappers whose outputs can diverge, and filter errors take a different path from controller errors.
  - B) Subclass Boot's `AbstractErrorWebExceptionHandler` / `DefaultErrorWebExceptionHandler` and reshape `ErrorAttributes` into the envelope. Rejected: it renders through Boot's error-attributes model (`server.error.*`, whitelabel, a router function) only to discard it, and ties the contract to Boot internals.
  - C) RFC 9457 problem details. Rejected: OpenAI SDKs read `body["error"]["message"]`. A problem+json body gives them `Error code: 404` with no message and no `code`, which breaks drop-in (ADR-004). One envelope everywhere also gives the CLI (CLI-01) one shape to parse.
  - D) Own `GatewayErrorWebExceptionHandler` implementing Boot's `ErrorWebExceptionHandler` marker, order −2. Boot's default backs off (missing-bean condition) and no `@ControllerAdvice` exists anywhere (ARCH-10). Handlers raise `GatewayErrorException`. The body is written with the application's configured `HttpMessageWriter`s.
- **Decision:** D.
  - JSON goes through the codecs rather than a direct Jackson call, so GW-01's JSON-library choice applies to errors unchanged. The exact-body integration test catches any shape regression, for example a serializer that drops `null` members.
  - Committed responses are not rewritten. GW-02 emits the SSE error event, using the same `toReply` and DTO.
- **Consequences:**
  - Every error path, filter or controller or codec, produces byte-identical envelopes for the same `GatewayError`.
  - `spring.webflux.problemdetails.enabled` must stay `false`: it registers an advice that would intercept errors first.
  - Exceptions are the transport only at the HTTP edge. Core never throws for expected failures.
  - Buys: fewer moving parts (Boot's handler and its attributes model are gone), one place to review, and the boundary for GW-02 is explicit.
- **Date:** 2026-11-03

### ADR-FND-04-006: How FND-04 proves its behaviour without product endpoints
- **Context:** The only production endpoint is actuator health. Proving 400, 405, 406, 413, 415 and 500 needs handlers that consume and produce JSON, and those belong to GW-01.
- **Options considered:**

Static resource mappings are switched off (`spring.web.resources.add-mappings: false`), so an unknown path is a plain `DispatcherHandler` 404 rather than a classpath lookup.
- **Consequences:** The full application context, the real filter order and real Netty are tested, with no production surface added. GW-01 inherits the tests and adds endpoint-specific ones. The `gateway-smoke` line is exercised once FND-03 makes smoke runs possible.
- **Date:** 2026-11-03

### ADR-FND-04-007: ARCH-10, error handling only in the `.error` package
- **Context:** The easiest way to break "one mapper" is a `@RestControllerAdvice` added with a new endpoint. It would win for controller and handler-mapping errors (via `DispatchExceptionHandler`) and silently change the body for those paths. Tests on existing endpoints would stay green.
- **Options considered:**
  - A) Rely on review. Rejected: the failure is silent.
  - B) Konsist rule ARCH-10 (section 7 table) with a violating fixture, reusing ARCH-6's annotation resolution and the inline-name matcher.
  - C) A runtime test asserting that no `@ControllerAdvice` bean exists. Rejected as the only guard: it checks one context, not every app module and test configuration, and fails late. Kept as a cheap extra: the single-`ErrorWebExceptionHandler` assertion.
- **Decision:** B, applying to all modules. The allowed location is `<root of an app-role module>.error`, so AGT-01's agent-app gets the same rule for free.
- **Consequences:** The rule set becomes ARCH-1 to ARCH-10 (CLAUDE.md Testing line). Its fixture follows [`architecture-rule-with-violating-fixture`](../knowledge/patterns/architecture-rule-with-violating-fixture.md). A typealias or subclass of a handler type declared inside `.error` and used elsewhere is not detected (names, not types); the bean-set assertion in `ErrorEnvelopeIntegrationTest` covers it. Buys: the "one place" rule of CLAUDE.md becomes a build failure instead of a review comment.
- **Date:** 2026-11-03

### ADR-FND-04-008: Startup warm-up of what the first request would do on an event loop
- **Context:** The first BlockHound run in `gateway-app` (2026-11-03) failed on two first-use paths: `ReactiveFlowKt`'s static `ServiceLoader` read in every `CoWebFilter`, and kotlin-reflect's built-ins read and contended locks in every Kotlin annotated handler. Only `ProbeController` is an annotated handler today; GW-01 may add more.
- **Options considered:**
  - A) A BlockHound allowance for the two paths. Rejected: it hides a real stall of the event loop, and allowing `InvocableHandlerMethod$KotlinDelegate.invokeFunction` would also hide blocking in the handler it invokes.
  - B) Warm kotlin-reflect in the test-only `ProbeController`. Rejected: the tests would pass while a production controller still stalled its first calls.
  - C) One production bean, `EventLoopWarmup`, doing both in `afterSingletonsInstantiated`, for every Kotlin handler in `RequestMappingHandlerMapping`.
- **Decision:** C. With no Kotlin handler registered it only initialises `ReactiveFlowKt`.
- **Consequences:** A new Kotlin controller is warmed without further work, and startup pays the cost. Handlers registered after startup are not warmed. Coroutine `coRouter` handlers need none of it.
- **Date:** 2026-11-03
